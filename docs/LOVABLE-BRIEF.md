# Lovable brief

Copy-paste prompts for continuing this project in Lovable. Two things to know before you
start:

- **Paste one numbered prompt at a time**, and check the diff before moving on. A single
  giant prompt produces sloppy work across many files.
- **Paste Prompt 0 first, and re-paste it after any long session.** It stops Lovable from
  reverting the July 2026 cleanup. Several of those files are ones Lovable considers its
  own and will regenerate unless told not to.

## Prompt 1 — commit the real database schema (highest priority)

This is the one thing Lovable can do that a local agent cannot: it has direct access to
your Supabase project.

```
Our supabase/migrations/ folder cannot rebuild the database. src/integrations/supabase/types.ts
describes tables that no migration file creates:

patient_sources, monthly_patients, clinics, clinic_brand_settings, google_business_tokens,
google_reviews, review_replies, review_sync_log, source_tags, user_invitations,
patient_changes_log, plus the dashboard_summary and office_metrics views.

patient_sources is the most important table in the product. These objects were applied
directly to the live project instead of through migrations, so there is no way to stand up
a local or staging database, and no rollback path for a schema change.

Please fix this:
1. Dump the current production public schema from the connected Supabase project —
   tables, views, functions, triggers, RLS policies, indexes, and constraints.
2. Commit it as ONE new baseline migration at the START of the migration order, named so
   it sorts before every existing file, e.g.
   supabase/migrations/00000000000000_baseline_schema.sql
3. Make it idempotent (CREATE TABLE IF NOT EXISTS, CREATE OR REPLACE, DROP POLICY IF
   EXISTS before CREATE POLICY) so it can run against the existing database without
   erroring.
4. Do not delete or rewrite the existing migration files.
5. Tell me explicitly whether `supabase db reset` now reproduces a schema the app runs
   against, and list anything you could not capture.

Do not change any application code in this task.
```

**Check before accepting:** the new file should contain `CREATE TABLE ... patient_sources`
and RLS policies for every table. If `patient_sources` is missing, the task failed.

## Prompt 2 — set the digest cron secret

`send-biweekly-digest` was callable by anyone and emailed every user; it now fails closed
until this secret exists, so **the digest is currently not sending**.

```
supabase/functions/send-biweekly-digest/index.ts now requires an x-cron-secret header that
it compares against the DIGEST_CRON_SECRET function secret, and it fails closed when that
secret is unset. This is intentional — the function runs on the service-role key and emails
every user, and it previously had no authentication at all.

Please:
1. Generate a random 32-byte hex value.
2. Store it as the DIGEST_CRON_SECRET Edge Function secret in the connected Supabase project.
3. Find whatever schedules this function (a pg_cron job, a Supabase scheduled function, or
   an external scheduler) and add the header `x-cron-secret: <that value>` to the request.
   If nothing currently schedules it, tell me — do not invent a schedule.
4. Confirm the function returns 401 without the header and 200 with it.

Do not weaken or remove the secret check to make this easier.
```

## Prompt 3 — enforce login rate limiting server-side

```
Our login rate limiting is client-side only and therefore not a real control.
src/contexts/AuthProvider.tsx tracks failed attempts in localStorage under the
"auth_rate_limit" key (5 attempts, 15 minute lockout). An attacker just clears
localStorage, opens a private window, or calls the Supabase auth endpoint directly.

The database already has a rate_limit_log table and a check_rate_limit function that this
flow never touches.

Please add real server-side enforcement:
1. Review the existing rate_limit_log table and check_rate_limit function and tell me what
   they currently do before changing anything.
2. Enforce a limit keyed on email address, recorded server-side, that survives the client
   clearing its storage.
3. Keep the existing localStorage lockout in AuthProvider.tsx as UX feedback — do not
   remove it — but it must no longer be the only thing standing between an attacker and
   unlimited attempts.
4. Explain where the enforcement runs and what happens when the limit is hit.

Do not move the auth subscription or timers out of AuthProvider.tsx while doing this.
```

Also a decision for you, not for Lovable. The database has a complete clinic/team model —
`clinics`, `clinic_brand_settings`, `user_invitations`, `get_user_clinic_id`, `get_user_role`,

have paying customers whose data is shaped by the answer.

## Not worth handing to Lovable

Two roadmap items are poor fits, because both need consistent judgement applied across
hundreds of sites and Lovable will paper over what it cannot fix:

- **Turning on `strictNullChecks`** (ROADMAP item 3). Lovable will scatter `!` and `?? ''`
  to silence errors, which hides exactly the crashes the flag exists to reveal. Do this
  directory by directory by hand.
- **The 388 lint warnings** (ROADMAP item 4), especially the ~35
  `react-hooks/exhaustive-deps` ones. Each needs a decision about whether the dep is truly
  missing or the effect is wrong, and a blanket "fix the warnings" pass will introduce
  render loops.
